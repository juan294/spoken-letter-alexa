# Alexa skill interaction model and conversational UX

Remediation plan for the friction recorded in `docs/friction-log.md`, section
"2026-09-10: first unscripted conversation on a real Echo". That entry is the evidence
base; this plan does not restate its measurements except where a phase's acceptance
criterion depends on a number.

Phases here are numbered 1–4 **within this plan**. They are unrelated to phases 0–9 of
`docs/plans/2026-09-03-alexa-plus-mcp-add-on.md`, which are complete.

- Phase files: `docs/plans/2026-09-10-alexa-skill-interaction-ux-phases/phase-1.md` … `phase-4.md`
- Base: `develop` at `522ab4e`
- Implementation happens in a worktree off `develop`, one phase per session
- Local gate, run sequentially, never as parallel Bash calls:
  `pnpm typecheck && pnpm lint && pnpm test && pnpm -F infra synth`
  (declared in `.rpi/policy.json`, run by `python3 .rpi/scripts/rpi-verify.py`)

## 1. The problem in one paragraph

The skill works and is slow, and when it fails it fails silently. Turn latency is
entirely model round trips — MCP tool calls cost 0.02–0.33 ms server-side and 9.9–25.4 ms
client-side, while each model round trip costs about 2.8 s — so a two-tool turn measured
6892 ms against the 7 s abort in `packages/skill/src/agent-client.ts` and Alexa's ~8 s
ceiling. One play request spent 6357 ms, called no tools and played nothing, and the
current `skill_turn` log line cannot say why. Separately the skill advertises an utterance
that cannot succeed, declares the `AUDIO_PLAYER` interface without the playback intents
that go with it, and answers every `AudioPlayer.*` event with an empty response so a
story ends into silence.

## 2. Scope

In scope, ordered by payoff:

1. Turn telemetry that can explain a turn (Phase 1)
2. Perceived latency: fewer model round trips per turn, and a progressive response over
   the remaining wait (Phase 2)
3. Interaction model, slot types and manifest copy (Phase 3)
4. Conversation shape and the spoken copy the Lambda produces (Phase 4)

Out of scope: the Phase 3 private-repository bridge (frozen until 2026-09-30, per
`AGENTS.md` Boundaries); anything touching `../spoken-letter`; the Alexa+ add-on path,
which does not go through `packages/skill` at all.

## 3. Decisions

**D-U1 — Extend the generator, never hand-edit the interaction model.**
`packages/skill/skill-package/interactionModels/custom/en-US.json` is generated by
`packages/skill/src/model/generate.ts` and a test fails when the committed file drifts
from the generator's output. Every model change in Phase 3 is a change to
`generate.ts` followed by `pnpm -F skill generate`. Resolved from repository evidence.

**D-U2 — Phase 1 is a hard gate.** Phases 2–4 begin only after the telemetry from Phase 1
is deployed and one real device conversation has been recorded. The 6357 ms zero-tool turn
and the identity of the sub-40 ms empty responses are both unexplained today, and both
Phase 2's design and Phase 4's dead-end fix are shaped by what that data shows. Owner
decision, 2026-09-10.

**D-U3 — Whether simple intents bypass the model is deferred to the Owner, not decided
here.** Slot-free `PlayStoryIntent`, `WhatIsNewIntent` and `NextStoryIntent` need
`list_family_stories`, `suggest_next_story` and "the newest story" respectively — no
language model is required to serve any of them. Calling MCP directly from the skill
Lambda would put those turns at roughly 300 ms instead of ~3 s.

| | Keep every turn agentic | Fast-path the three simple intents |
| --- | --- | --- |
| Simple-turn latency | ~3.1 s after Phase 2 | ~300 ms |
| Where Bedrock/Strands visibly works | every spoken turn | `CatchAllIntent` and slotted `PlayStoryIntent` only |
| AWS Builder mini challenge | strongest possible story | still satisfied — every service does real work in code and is documented — but a judge watching the demo sees the agent on fewer turns |
| Cost per turn | one to two Bedrock calls | zero on three of five intents |
| Added complexity | none | a second code path in the skill Lambda, plus MCP credentials in a Lambda whose role currently holds nothing beyond logs and X-Ray |

Phase 2 is designed so this can be added afterwards without rework: the catalog the
session already holds is exactly what a fast path would read. The decision is best made
with Phase 1's measured turn durations in hand, and it is recorded here so it is not made
silently inside an implementation session.

**D-U4 — Two claims stay marked unverified until a phase discharges them.**

| Claim | How it gets discharged |
| --- | --- |
| Certification requires the AudioPlayer playback intents | Phase 3, `ask validate` against the regenerated model; the result is written into the phase file whichever way it lands |
| The sub-40 ms empty responses are `SessionEndedRequest` and `AudioPlayer.*` events | Phase 1, by logging the request type; no other evidence settles it |

Neither claim may be restated as fact anywhere in the repository until its phase records
the evidence.

## 4. Phase structure

| Phase | Outcome | Deploy gate |
| --- | --- | --- |
| 1 | A turn's request type, slots, spoken text, story id, duration and error class are in the log; turn duration and dead-end plays are CloudWatch metrics | **Owner `cdk deploy` + one real device session before Phase 2** |
| 2 | A play turn needs one model round trip, not two; the wait is spoken over | Owner `cdk deploy` |
| 3 | The model carries the playback intents, a storyteller slot type that matches real speech, no competing `SearchQuery` carriers, and a manifest that advertises real stories | **Owner `ask deploy` (skill metadata)** |
| 4 | A story leads somewhere; a play request never dead-ends; failures say what actually failed | Owner `cdk deploy` |

Every phase stops at its own acceptance gate. `AGENTS.md` reserves push, `ask deploy` and
every AWS mutation to the Owner.

## 5. Acceptance criteria

### Automated (every phase)

- `pnpm typecheck && pnpm lint && pnpm test && pnpm -F infra synth`, sequential, all pass
- No new `[NEEDS CLARIFICATION]` markers, no placeholder values
- Per-phase unit tests named in each phase file

### Manual (per phase, on a real Echo)

Phase-specific and listed in each phase file. The shared shape: one conversation of at
least six turns, with the CloudWatch log lines for that conversation pasted into the
phase file as evidence. A phase is not accepted on unit tests alone — the defects in this
plan are all defects of live behaviour, and three of them (the dead-end play, the silent
story end, the mis-routed `SearchQuery` carriers) cannot be observed in a unit test.

## 6. Risks

- **The catalog-injection win may not reproduce.** The 3216 ms vs 6892 ms comparison is
  two turns, not a distribution, and the fast turn also benefited from a warm container.
  Phase 2's acceptance criterion is therefore stated over at least ten turns from Phase 1
  telemetry, not over a single measurement.
- **A progressive response consumes part of the same budget.** The Directive Service call
  is an outbound HTTPS request from the skill Lambda. If it is issued synchronously before
  the agent call it makes the worst case worse. Phase 2 specifies it fire-and-forget with
  its own short timeout, never awaited on the critical path.
- **Adding playback intents can shift NLU routing for existing utterances.** `next one`
  currently reaches `NextStoryIntent`; `AMAZON.NextIntent` will compete for it. Phase 3
  keeps both and routes them to the same behaviour rather than choosing between them.
- **Deadline.** Submission is Friday 2026-10-23. Phases 3 and 4 are independently
  shippable; if time runs short, Phase 3 is the one that matters for certification and
  Phase 4 is the one that matters for the demo video. Phase 2 is pure quality-of-life and
  can be dropped last.
